What Is a Commit? The Snapshot That Saves Your Work

You have heard the word "commit" dozens of times. Here is what it actually is — and why it is the single habit that separates people who can recover from mistakes from people who start over from scratch.

THE 2-MINUTE VERSION

  • A commit is a permanent saved snapshot of every file in your project at one specific moment.
  • Each commit gets a unique ID (called a hash) and a short message you write describing what changed.
  • Commits chain together in order — that chain is your full project history, and you can rewind to any point in it.
  • Two commands make it happen: git add stages the files, then git commit seals the snapshot.
  • Your repo already auto-commits at the end of every Claude Code session — you have a history right now and may not know it.

The Camera Analogy

Picture your project folder as a film set. Every file in it — your Python scripts, your HTML pages, your config files — is a prop sitting in a specific position. A commit is a photograph of the entire set at one moment. Every prop, every position, captured exactly as it is right now.

That photo gets stored permanently in your repository (the special folder that tracks history, covered in Issue #5). Next week, if something breaks and you cannot figure out why, you flip back through the photo album and find the exact moment everything still worked. That is the whole point.

What Is Actually Inside a Commit

Every commit contains three things:

  • A snapshot — the full state of every file Git is tracking at that moment.
  • A message — a short note you write, like "Fixed invoice export bug." This is the caption on the photo.
  • A hash — a unique ID that Git (the version-control software introduced in Issue #6) generates automatically. It looks like a3f4b2c. No two commits in the history of your project will ever share the same hash.

You never write a hash yourself — Git does that. But knowing what one is stops phrases like "revert to commit a3f4b2c" from sounding like a foreign language. It just means: "Put everything back to that exact photograph."

How Commits Chain Together

Commits do not exist in isolation. Each one points back to the commit before it — like links in a chain. That chain IS your project history. The newest commit is at the front; the very first one you ever made is at the far end.

When you run git log in your terminal (the text-based interface on your Mac where you type commands), Git walks that chain backward and prints every snapshot: its short hash, the author, the date, and the message. It is a timestamped diary of every meaningful change ever made to your project.

The Two Commands That Make a Commit

Making a commit is a two-step process. Think of it like packing a box and then sealing it:

git add .                   # Step 1: Pack all changed files into the box
git commit -m "Your message"  # Step 2: Seal the box and label it

git add . — The dot means "all changed files in this folder." This step is called staging. You are telling Git which files to include in the next snapshot. Git does not automatically include every changed file — you have to declare what matters. The dot is the lazy shortcut for "include everything."

git commit -m "message" — The -m flag stands for "message." Whatever you put in the quotes becomes the caption on your snapshot. Good messages say what changed and why — "Added client name field to invoice form" beats "update" every single time.

Saving a File vs. Committing — They Are Not the Same Thing

This trips up almost every beginner. When you hit Cmd+S in a code editor, you save the file to your hard drive. That is just writing bytes to disk. Git has no idea it happened.

A commit is something you do on top of saving. You save the file first, then you stage it with git add, then you commit. Only then does Git record a permanent snapshot. A saved-but-not-committed file is like a note on a sticky pad: it is there right now, but it is not in the archive. If you delete the file or accidentally overwrite it before committing, Git cannot help you get it back.

Why This Matters for You

Your footage organizer, your Payday app, and your caption scripts all live in graydavis33/my-project. Every time Claude Code finishes a session, it runs git add and git commit on your behalf. You already have a stack of snapshots — you just did not know what to call them.

Here is where this pays off in a real situation: Claude rewrites your invoice tracker and the export feature stops working. Before commits, you would be digging through memory trying to recall what changed. With commits, you open the terminal, run git log --oneline, find the last snapshot where export worked, and look at exactly what was different. No guessing. No rebuilding from scratch.

TRY THIS TODAY

Open your terminal on your Mac, navigate to your project folder, and run this:

git log --oneline

You will see a list: one commit per line, each with a short hash and the message Claude wrote when it auto-committed. That is your project's photo album. Count the entries — every line is a version of your tools you could return to if something broke.

Tip: if you are not sure how to navigate to the folder in the terminal, open the terminal, type cd (with a space after it), then drag your project folder from Finder onto the terminal window. It will fill in the path for you. Then press Enter.

Test Yourself

1. In one sentence, what is a commit?

Answer: A commit is a permanent, labeled snapshot of every tracked file in your project at one specific moment in time. This is the core definition — everything else about version control is just different ways of working with these snapshots.

2. What three things does every commit contain?

Answer: A snapshot of all tracked files, a message describing what changed, and a unique hash (ID). Together these let you identify, understand, and restore any point in your project's history.

3. What is a commit hash, and do you have to write it yourself?

Answer: A hash is a unique auto-generated ID (like a3f4b2c) that Git creates for each commit — you never write it yourself. It guarantees no two commits can ever be confused with each other, even across different projects or machines.

4. What does git add . do, and why is the dot significant?

Answer: It stages all changed files — it tells Git to include everything in the current folder in the next snapshot. The dot is shorthand for "this folder and everything inside it." Without this step, git commit has nothing to snapshot and will not do anything useful.

5. What does the -m flag stand for, and what makes a commit message good?

Answer: It stands for "message." A good message describes what changed and why — something like "Fixed invoice total rounding error" instead of just "fix." Your history is only as useful as its labels; vague messages force you to open files to figure out what a snapshot even contains.

6. What is the difference between saving a file and committing it?

Answer: Saving writes the file to your hard drive — Git is not involved and does not notice. Committing tells Git to permanently record a snapshot. A saved-but-not-committed file is invisible to your history; if you accidentally delete or overwrite it, Git cannot recover it for you.

7. How are commits connected to each other?

Answer: Each commit points back to the one before it, forming a chain. The newest commit is at the front and the very first commit is at the end. That chain is your complete project history — Git uses it to show you what changed between any two points in time.

8. What command shows your full commit history, and what does the --oneline flag add?

Answer: git log --oneline. Without the flag, git log prints the full hash, author, date, and message for every commit — useful but verbose. The --oneline flag compresses each commit to a single line so you can scan the whole history at a glance.

9. Does Gray need to run git commit manually after each Claude Code session? Why or why not?

Answer: No. His repo is configured to auto-commit and auto-push at the end of every Claude Code session, meaning Claude runs those commands on his behalf. He already has a full commit history building up automatically, even if he has never typed git commit himself.

10. Claude edits your caption scripts and suddenly they stop working. You have 20 commits in your history. What is the very first thing you do to investigate?

Answer: Run git log --oneline to see all 20 commits with their messages and hashes. Scan the messages to find the last session where the scripts were still working, then look at what changed in the commit after that. Commits give you a time machine — this is exactly the moment you use it.
