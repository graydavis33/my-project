Push and Pull: How Your Code Actually Gets to GitHub

You've been making commits — local snapshots of your work. But a commit by itself never leaves your computer. Push and pull are the two moves that actually sync your code with the world.

The 2-Minute Version

  • Your repo exists in two places: your computer (local) and GitHub (remote).
  • Push uploads your local commits to GitHub. Nothing reaches GitHub until you push.
  • Pull downloads commits from GitHub onto your machine. Do this before starting work on a second computer.
  • In the command git push origin main, "origin" is just GitHub's nickname and "main" is the branch name.
  • Gray's Claude Code already auto-pushes at the end of every session — so he's been doing this without realizing it.

Your Repo Lives in Two Places

Every time you work in your repo, you're working in the local copy — the one sitting on your Mac's hard drive (or your Windows PC). GitHub holds the remote copy — an identical version stored on GitHub's servers, accessible from any device with a browser.

These two copies do not talk to each other on their own. They stay in sync only when you explicitly tell Git to send or receive changes. That's what push and pull do.

Think of it like a Google Doc you also save as a Word file on your desktop. Editing the desktop file doesn't update the Google Doc. You have to manually upload it. Git is the same idea, just more precise about what gets sent.

Push: Sending Your Commits Up

Push takes the commits you've made locally and uploads them to GitHub. Until you push, those commits exist only on your machine. GitHub has never seen them.

The command is:

git push origin main

Break it down word by word:

  • git — the version-control tool you've been using all along.
  • push — the command meaning "send my commits outward."
  • origin — a nickname (alias) for the GitHub URL where your repo lives. When you first connect a local repo to GitHub, Git automatically names that remote address "origin." You could rename it to anything, but nobody does — "origin" is the universal default.
  • main — the name of the branch you're pushing. A branch is a named line of commits inside the repo. Your default branch is called "main." (You'll learn branches in detail in a future issue.)

After this command runs, anyone who opens your GitHub repo in a browser will see every commit you just pushed.

Pull: Bringing New Commits Down

Pull is the reverse. It downloads commits that exist on GitHub but haven't reached your local machine yet, then merges them into your current files.

The command is:

git pull origin main

Same structure — just the word "pull" instead of "push." Git downloads whatever is on GitHub that your local machine doesn't have yet, and applies it to your files.

When do you need this? Every time you switch computers. You push from your Mac. The next morning you sit down at your Windows PC. Your Windows copy of the repo is still where it was yesterday — it doesn't know about what you pushed from the Mac. Running git pull syncs it instantly.

The one rule: always pull before you start working on a machine that might be behind. If you skip this and make new commits on top of an old version, you'll create a conflict — two histories that don't agree on what happened. Conflicts are solvable, but a quick pull prevents them entirely.

The Full Cycle

When you're on one machine, the pattern is:

edit files → commit → push

When you switch to a second machine, the pattern becomes:

pull → edit files → commit → push

Pull first, always. Then you're safe to work. This is the same rhythm used by professional teams with dozens of developers — it scales from one person on two laptops to 50 engineers on one codebase.

Commit vs. Push: The Sharp Line

These two words are easy to blur together. Here's the clear difference:

  • A commit saves a snapshot to your local repo's history. Nothing leaves your machine.
  • A push ships one or more commits from your local history to GitHub's history.

You can make 20 commits in one afternoon, then push them all to GitHub in a single push command. The push bundles them up and sends the whole stack at once.

Why This Matters for You

Two concrete places push and pull are already running in your life:

1. Your Claude Code auto-push. Every time a Claude Code session ends, your setup runs git push automatically. That's why your work in graydavis33/my-project on GitHub always reflects your latest session — Claude Code committed the changes, then pushed them. You've been benefiting from push this whole time without writing the command yourself.

2. Switching between Mac and Windows. Say you spent Tuesday on your Mac building a new feature in your footage organizer. Wednesday you sit down at your Windows PC. If you open the project and start editing without pulling first, Windows is working from Tuesday's version — it missed everything you committed after that. One git pull origin main brings it current in seconds.

3. Your GitHub Actions workflows. Those cloud automations — including the one that generates this very email — are triggered when a push arrives at GitHub. No push, no trigger. This is why push is the "start signal" for so much of your automated stack.

Try This Today

Open your terminal, navigate to your project folder, and run:

git log --oneline -5

This shows your five most recent local commits. Then open your GitHub repo in a browser and compare. If they match, you're fully in sync. If GitHub shows commits your terminal doesn't, run:

git pull origin main

Test Yourself

1. What are the two "copies" of a repository, and where does each one live?

Answer: The local copy lives on your computer's hard drive. The remote copy lives on GitHub's servers. They are completely separate — changes in one do not automatically appear in the other. You have to use push or pull to sync them.

2. You made three commits on your Mac. Do those commits exist on GitHub yet?

Answer: No — not until you run git push. Commits are local snapshots only. Push is the separate step that sends them to GitHub.

3. What does git pull origin main actually do to your files?

Answer: It downloads any commits that exist on GitHub but are missing from your local machine, then applies them to your files. Your local copy catches up to whatever GitHub currently shows.

4. In git push origin main, what does "origin" refer to?

Answer: "Origin" is a nickname (alias) for the remote GitHub URL where your repo lives. Git sets this nickname automatically when you connect a repo to GitHub. It's a convention everyone follows — not a technical requirement — but you'll see it in every Git project.

5. What does "main" mean in that same command?

Answer: "Main" is the name of the branch being pushed. A branch is a named line of commits inside the repo. Your default branch is called "main," so you're telling Git: push commits from my local "main" branch up to GitHub's "main" branch.

6. You worked on your footage organizer all afternoon and made 5 commits. What is the correct final step to end your session?

Answer: Run git push origin main. That sends all 5 commits to GitHub at once. In your case, Claude Code's auto-push does this automatically at the end of every session — but now you know what it's actually doing.

7. You sit down at your Windows PC the next day. What is the very first Git command you should run before touching any code?

Answer: git pull origin main. Your Windows copy hasn't seen yesterday's push from the Mac. Pulling first brings it up to date so you're working on the latest version — not an outdated one that will cause a conflict later.

8. What is the key difference between a commit and a push?

Answer: A commit saves a snapshot to your local repo — nothing leaves your machine. A push ships those commits to GitHub. You can commit many times and push once to send them all. You cannot push without first committing — there's nothing to send.

9. Your GitHub Actions workflow — the one that generates this Daily AI Read email — only fires when new code arrives at GitHub. What action directly triggers it?

Answer: A push. GitHub Actions watches for incoming pushes to the repository and uses that event as the start signal. Without a push, GitHub never knows new commits exist, and the workflow never runs.

10. What could go wrong if you work on your Windows PC without pulling first, make new commits, then try to push?

Answer: You'd likely get a conflict — your Windows history and GitHub's history have diverged, so Git doesn't know how to combine them automatically. Git will block the push and ask you to resolve it. A quick pull before you start prevents this entirely.
