Git vs. GitHub — Two Different Things Everyone Confuses

Your code lives at github.com/graydavis33/my-project. But "Git" and "GitHub" are not the same thing — one is a tool on your computer, the other is a website in the cloud. Knowing the difference will make every future conversation about your code make sense.

The 2-Minute Version

  • Git is software. It runs on your computer and tracks every change you ever make to your code files.
  • GitHub is a website. It stores a copy of your Git repository online so it is backed up and reachable from anywhere.
  • You can use Git without GitHub. You cannot use GitHub without Git.
  • Push means sending your local changes up to GitHub. Pull means bringing changes from GitHub down to your machine.
  • You already use both every day — your Claude Code sessions auto-push to graydavis33/my-project at the end of each session.

Git: The Tool That Lives on Your Computer

Git is version-control software. "Version control" means it watches a folder and takes a snapshot every time you tell it to. Those snapshots are called commits (you learned about these in Issue #5). Each commit records exactly what changed, when, and — if you write a message — why.

Git was created in 2005 by Linus Torvalds, the same person who created the Linux operating system. He needed a way to manage thousands of contributors making changes to the same codebase without overwriting each other. Git solved that. git-scm.com is the official home of Git documentation — the "scm" stands for Source Code Management, another name for version control.

Think of Git like a very powerful Undo button that never expires. Normal Undo in Premiere goes away when you close the project. Git keeps every single save point forever, and you can jump back to any one of them.

GitHub: The Website That Hosts Your Git Repos

GitHub is a company and a website. Its job is to store Git repositories on its own servers so you can access them from any computer, collaborate with others, and keep a backup that is not on your hard drive.

The physical analogy: Git is your camera. It takes the pictures. GitHub is iCloud. It stores and syncs those pictures so they are safe and reachable from your phone, your laptop, or your PC. Your camera works fine without iCloud — you just lose the backup and the sync.

GitHub was founded in 2008 and acquired by Microsoft in 2018 for $7.5 billion. Today it hosts over 100 million developers and more than 420 million repositories. github.com/about has the current numbers. There are alternatives — GitLab, Bitbucket — but GitHub is by far the most widely used.

Push and Pull: The Two Directions of Sync

Once your repo exists on both your computer (called the local copy) and on GitHub (called the remote copy), you need a way to sync them. There are two directions:

Push — You did work on your Mac. Your local copy is ahead. You push your commits up to GitHub to update the remote. "Push" always means local to remote.

Pull — You switched to your Windows PC. GitHub has commits that your PC does not. You pull from GitHub to bring those commits down. "Pull" always means remote to local.

That is the entire sync loop. Push when you are done on one machine. Pull before you start on another. Right now, Claude Code handles both for you automatically at the end of each session — but knowing these terms means you will understand what it is doing and can run them yourself if something breaks.

Why Public Repos Are Useful (and What to Watch Out For)

Your repo graydavis33/my-project is public, which means anyone on the internet can view the code. This is fine and common — most open-source software in the world lives on public GitHub repos. It is how other developers and tools (including Claude Code itself) can read your code to help you improve it.

One rule you must never break: do not put secrets in a public repo. A secret is anything like a password, an API key (a private code that lets you access a paid service), or your bank login. If a secret ends up in a file that gets pushed to GitHub, anyone searching the internet can find it within minutes, and automated bots scan GitHub constantly looking for exactly this. GitHub docs on secret scanning explains the risk. You will learn about API keys and how to store them safely in a future issue.

Everything else — your footage organizer logic, your Payday app code, your caption scripts — is fine to live publicly.

Why This Matters for You

You already live inside this system. Every Claude Code session ends by committing your work and pushing it to graydavis33/my-project. Your GitHub Actions — the automations that run your tools in the cloud — are triggered by those pushes. When you push, GitHub sees the new commit and fires the action. That is the entire chain.

When you sit down at your Windows PC and open a project you worked on yesterday on your Mac, the move to make is: pull first. That one habit prevents your two machines from getting out of sync and creating the painful situation where you have two different "latest" versions of the same file.

Try This Today

Open your browser and go to github.com/graydavis33/my-project.

You will see a list of files. Click any file to read the code. Then click the clock icon labeled "History" or "commits" at the top right of the file view. You are looking at every commit ever made to that file — every snapshot Git took. Click one. GitHub will show you exactly what changed: red lines were deleted, green lines were added.

That is Git and GitHub working together, live, in your actual project. Five minutes, no new software needed.

Test Yourself

1. What is Git, in one sentence?

Answer: Git is version-control software that runs on your computer and takes snapshots (commits) of your code every time you tell it to. It exists because without it, every file edit is permanent and irreversible — Git gives you an infinite, named Undo history.

2. What is GitHub, and how is it different from Git?

Answer: GitHub is a website that stores Git repositories online. Git is the tool that creates and manages those repos on your local machine. GitHub provides the cloud backup and sync layer — without it, your repo exists only on one computer.

3. Can you use Git without GitHub?

Answer: Yes. Git runs entirely on your local machine and will track commits without any connection to the internet or GitHub. You just lose the backup, remote access, and automation features that GitHub adds.

4. What does "push" mean?

Answer: Push means sending your local commits from your computer up to GitHub. Think of it as uploading your latest snapshots to the cloud. Your Claude Code sessions do this automatically at the end of each session.

5. What does "pull" mean?

Answer: Pull means downloading commits from GitHub onto your local machine. You need to do this whenever GitHub has newer commits than your local copy — for example, when you switch from your Mac to your Windows PC.

6. You finish a Claude Code session on your Mac on Monday. Tuesday you sit down at your Windows PC to keep working. What should you do before writing a single line of code?

Answer: Pull from GitHub first. Your Mac session auto-pushed Monday's commits, but your PC does not have them yet. If you skip the pull and start writing, you create two conflicting "latest" versions that Git has to reconcile — which causes merge conflicts and extra work.

7. What is a "local" copy of a repo vs. a "remote" copy?

Answer: Local is the copy on your computer's hard drive. Remote is the copy hosted on GitHub's servers. They are the same repo, just stored in two places. Push and pull are the actions that keep them in sync.

8. Your repo is public. Why is that fine for your code, but dangerous if you add a file containing an API key?

Answer: Code logic is safe to share publicly — there is nothing harmful about someone reading how your footage organizer works. But an API key is like a password that grants access to a paid service on your behalf. If it is in a public repo, automated bots will find it within minutes and can use it to run up charges or steal data in your name.

9. Who created Git, and what problem was it originally solving?

Answer: Linus Torvalds created Git in 2005. He needed a way for thousands of contributors to make changes to the Linux operating system without overwriting each other's work. Git tracks who changed what and when, so conflicts can be detected and resolved.

10. How does GitHub connect to the GitHub Actions automations already running your tools in the cloud?

Answer: GitHub Actions listens for events on your repo — the most common one is a new push. When Claude Code auto-pushes at the end of your session, GitHub detects the new commit and triggers whatever action you have configured. That is why your cloud tools update automatically without you manually deploying anything.
