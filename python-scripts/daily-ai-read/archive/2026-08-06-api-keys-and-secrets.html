API Keys Are Passwords for Your Code — Keep Them Secret

Your tools already talk to outside services using API keys. If one of those keys ends up in your public repo, automated bots will find it — and use your account — within minutes. Here is what a key actually is, where it belongs, and how to check you are already safe.

The 2-Minute Version

  • An API key is a long unique code that proves to a service which account is making a request.
  • Never paste a key directly into a code file — that is called hardcoding and it is dangerous.
  • Keys belong in a .env file that stays on your machine and never goes to GitHub.
  • Your .gitignore file tells Git which files to skip — .env must always be on that list.
  • For tools running in the cloud (like your GitHub Actions email agent), keys live in GitHub Secrets — encrypted storage only your workflows can read.

What an API Key Actually Is

In Issue #11, you learned that an API is a messenger — a way for your code to ask another service to do something. An API key is the ID badge your code flashes at the door so the service knows which account to let in.

Think of a library card. The library does not ask your name or password every time you check out a book — you just show the card and they scan it. Your API key works the same way. It is a long random string of letters and numbers (something like sk-ant-api03-xK7mP2aBcD...) that goes along with every request your code sends. The service checks the key, recognizes your account, and responds.

Services use keys for three reasons: to charge the right account, to limit how many requests any one account can make, and to cut off access instantly if something goes wrong.

The Danger: Hardcoding

"Hardcoding" means pasting the actual key value directly into a code file. It looks like this:

api_key = "sk-ant-api03-xK7mP2aBcDeFgH..."

The problem: your repo is public. Anyone on the internet can browse graydavis33/my-project. The moment a file with a hardcoded key is pushed to GitHub, it is exposed. And it happens fast — security researchers at GitGuardian have documented automated bots scanning new GitHub commits and snatching keys within seconds of publication.

A stolen key means someone else can impersonate your account, rack up charges, or delete data — and the service may not refund you, because technically your credentials authorized it.

The Fix: the .env File

A .env file (say "dot env") is a plain text file that lives in your project folder. Its only job is to hold sensitive values. It looks like this:

ANTHROPIC_API_KEY=sk-ant-api03-xK7mP2...
BANK_API_KEY=xyz789abc...

Your code reads values from this file at runtime. The file stays on your machine. It never goes to GitHub.

To guarantee it never goes to GitHub, you add it to your .gitignore file. You learned about commits in Issue #7 — the .gitignore is a file that tells Git "skip these items when packaging a commit." Once .env is listed there, Git will never include it in any snapshot, and it will never be pushed to your repo.

One side effect: because .env is excluded from GitHub, it does not sync to your Windows PC when you pull the repo there. You need to manually copy the .env file to each machine you work on — or recreate it by pasting your keys in fresh.

Cloud Tools Need a Different Solution: GitHub Secrets

Your email agent runs automatically via GitHub Actions — the cloud system that runs your scheduled tools. But GitHub Actions cannot read a .env file sitting on your Mac. Your Mac is not even involved when that cloud job fires. The remote server GitHub spins up to run the job has no connection to your hard drive.

GitHub Secrets solve this. They are encrypted key-value pairs stored inside your repository settings on GitHub. When a GitHub Actions job runs, it can access those secrets the same way code reads from a .env file — but the values are never visible in your code, never printed in run logs, and never exposed to the public. Even you cannot read the value back out after you save it.

You set them once in your repo's settings (Settings → Secrets and variables → Actions), then reference them in your workflow file as secrets.ANTHROPIC_API_KEY. That is it.

If a Key Leaks: Rotate It

"Rotating" a key means replacing it. If you suspect a key was exposed — or you know you pushed it by accident — go to that service's settings, delete the old key, and generate a new one. The old key stops working immediately. Think of it like changing your password after a breach.

Deleting the old key is the critical step. Removing it from your code file is important too, but even after you edit the file, the old key still lives in your Git history unless you take extra steps. Rotating the key at the source makes the leaked value useless regardless of where it ended up.

Why This Matters for You

Count the API-connected tools you already have running. Your Payday app syncs with a bank — almost certainly via an API key. Your email agent makes API calls to send and receive messages. The Daily AI Read emails you are getting right now were generated by code that calls Anthropic's API, which requires a key. Your auto-caption scripts likely call a transcription API too.

All of those keys need to live in .env (on your machine) and GitHub Secrets (for cloud runs). Because graydavis33/my-project is public, a single hardcoded key is effectively a public key. This habit costs nothing to build now and can cost a lot to skip.

Try This Today

Audit your repo for exposed keys. Takes 5 minutes.

  1. Open your project folder on your Mac. Look for a file named .gitignore. Open it in any text editor and confirm .env appears on its own line. If it does not, add it now and save.
  2. Go to github.com/graydavis33/my-project in your browser. Use the search bar at the top of the repo page and search for API_KEY. If any result shows an actual key value pasted inside a code file, that key is already public — rotate it at the service's settings page immediately.
  3. Check your GitHub repo settings (Settings → Secrets and variables → Actions) and confirm any keys your cloud tools need are already stored there as Secrets.

Test Yourself

1. In plain terms, what is an API key?

Answer: A unique string of characters a service gives you to identify your account when your code makes a request. It is the equivalent of an ID badge — the service checks it to know who to charge, how much to allow, and whether to grant access at all.

2. What does "hardcoding" an API key mean, and why is it risky?

Answer: Hardcoding means pasting the actual key value directly into a code file (e.g., api_key = "sk-abc123..."). It is risky because if that file ever gets pushed to a public repo, the key is readable by anyone — including automated bots that scrape GitHub looking for exactly this pattern.

3. What is a .env file, and what does it store?

Answer: A plain text file that lives in your project folder and stores sensitive values — API keys, passwords, account IDs — as named variables. Your code reads from this file at runtime instead of having the values written directly into the code. The file stays on your machine and is never pushed to GitHub.

4. What does a .gitignore file do, and why must .env be listed in it?

Answer: A .gitignore file tells Git which files to skip when creating a commit — those files are never included in any snapshot and therefore never pushed to GitHub. Listing .env there ensures your API keys stay on your machine no matter how many commits and pushes you make.

5. Gray's email agent runs on GitHub Actions in the cloud. Why can't it just read his local .env file?

Answer: The .env file exists only on Gray's Mac. When GitHub Actions runs a scheduled job, it runs on a remote server inside GitHub's cloud infrastructure — his local machine is completely uninvolved. That remote server has no access to files on his hard drive.

6. What are GitHub Secrets, and how do they differ from a .env file?

Answer: GitHub Secrets are encrypted key-value pairs stored in your repository's settings on GitHub. Unlike a .env file (which lives on your machine), Secrets are accessible to GitHub Actions workflows running in the cloud. Once saved, the values are encrypted and cannot be read back — not even by you — only used by running workflows.

7. Gray accidentally commits a hardcoded Anthropic API key to his public repo. What should he do first — edit the code file or rotate the key?

Answer: Rotate the key first. Go to Anthropic's console, delete the old key, and generate a new one. The old key becomes useless the instant it is deleted — regardless of where else it appears. Editing the code file matters for future safety, but it does not retroactively protect the key already visible in the commit history.

8. What does "rotating" a key mean?

Answer: Replacing an API key with a new one. You go to the service's settings, delete (invalidate) the old key, and generate a fresh key. The old key stops working immediately. Then you update your .env file and GitHub Secrets with the new value. It is the API-key equivalent of changing your password after a breach.

9. Gray checks his Anthropic billing page and sees thousands of API calls he did not make. What is the most likely explanation, and what should he do?

Answer: His API key was most likely exposed — possibly hardcoded in a file pushed to his public repo, where a bot found it and began using it. The immediate fix: rotate the key at Anthropic's console. Then search his repo for hardcoded values and move any keys into .env and GitHub Secrets.

10. Gray switches to his Windows PC and pulls the repo from GitHub. His tools fail immediately. What is missing and why?

Answer: The .env file. Because .env is listed in .gitignore, it was deliberately never pushed to GitHub — which is correct behavior. But that also means it does not appear when he pulls the code to a new machine. He needs to manually copy the .env file from his Mac to his Windows PC, or recreate it there by pasting his keys in fresh. This is a feature, not a bug: the keys never travel through GitHub where they could be exposed.
