The .env File: How Your Code Reads Secrets Without Storing Them

Last issue you learned that API keys are passwords for your code. Today: the file that holds those passwords safely — and why it must never go to GitHub.

THE 2-MINUTE VERSION

  • An environment variable is a named value the computer holds in memory, available to any program that asks for it — not stored in your code.
  • A .env file is a plain-text file in your project folder where you list those values during development on your laptop.
  • The .env file never gets committed to Git — you put its name in a file called .gitignore so Git ignores it completely.
  • When your code runs in the cloud (GitHub Actions), GitHub's Secrets panel replaces .env — same idea, just cloud-hosted.
  • Your email agent, your Payday bank sync, and your GitHub Actions automations are all using this system right now, even if you've never noticed it.

The Problem That Made This Necessary

You have code that needs a secret. Maybe it's your Anthropic API key so Claude can respond, or your bank's login credentials so Payday can sync. The code needs that secret to run.

The obvious move: just put the secret directly in the code file. Like this:

api_key = "sk-ant-api03-AbCdEfGhIjKl..."

The problem: that code file lives in your GitHub repo. Your repo is public. GitHub is searchable. Automated bots scan every public repo on GitHub constantly, hunting for exposed API keys. If they find yours, they will use it — running up charges or stealing data — often within minutes.

So the rule in software is simple: secrets never live in code files. They live somewhere else. That somewhere else is environment variables.

What an Environment Variable Actually Is

Think of your computer like a restaurant kitchen. The recipe (your code) says "add the secret sauce." But the recipe doesn't write out what's IN the secret sauce — that's stored in a locked box on the shelf. The recipe just says "go get the bottle labeled SECRET_SAUCE." Any cook in that kitchen can read the recipe, but only someone with access to that shelf can actually make the dish.

An environment variable is the labeled bottle on that shelf. It's a named value that exists in the computer's memory — not in any file you write. The computer (or the cloud server) holds it. Your code just asks for it by name.

In Python (which many of your tools are written in), you retrieve an environment variable like this:

import os
api_key = os.environ["ANTHROPIC_API_KEY"]

The code file has zero secrets in it. It just knows the name of the shelf where the secret lives. You could post this code publicly on GitHub and it would reveal nothing.

The .env File: Your Local Secret Shelf

Setting environment variables one by one through the terminal gets tedious fast. So developers created a convention: a file named .env.

That filename is just a dot followed by "env" — the dot is part of the name. On a Mac, files that start with a dot are hidden by default (they don't show up in Finder unless you press Cmd+Shift+Period). This is intentional — a subtle signal that the file is special and shouldn't be casually opened or shared.

The file itself looks like this — just a list of names and values, one per line:

ANTHROPIC_API_KEY=sk-ant-api03-AbCdEfGhIjKl...
BANK_SYNC_TOKEN=eyJhbGciOiJIUzI1N...
EMAIL_SMTP_PASSWORD=mySuperSecretPass!

When your code starts up, a small library (often called python-dotenv in Python) reads this file and loads all those values into the computer's memory as environment variables. From that point on, your code can retrieve them by name using os.environ[...].

The .env file lives on your laptop, locally. It never travels anywhere. Which brings us to the most important rule.

The One Rule: .env Goes in .gitignore

A file called .gitignore sits in your project folder and tells Git: "never track these files, never commit them, never push them to GitHub." Every line in .gitignore is a filename that Git will completely ignore.

Your .gitignore file should always have this line:

.env

With that in place, no matter how many times you commit and push, your .env file stays on your laptop only. Git treats it like it doesn't exist.

Most projects also include a companion file: .env.example. This has the same structure as .env but with actual values swapped for placeholders:

ANTHROPIC_API_KEY=your_api_key_here
BANK_SYNC_TOKEN=your_token_here
EMAIL_SMTP_PASSWORD=your_email_password_here

.env.example IS safe to commit to GitHub. It tells anyone reading your repo exactly which environment variables the project needs — without exposing any actual values. It's the recipe card that says "you'll need the secret sauce" but doesn't say what's in it.

The Cloud Version: GitHub Secrets

When your code runs in the cloud — like your GitHub Actions automations — there's no laptop and no .env file. The cloud server has never seen your local files. So where do the secrets come from?

GitHub has a built-in system for this: Secrets. You go to your repo on github.com → Settings → Secrets and variables → Actions → New repository secret. You type the name (e.g., ANTHROPIC_API_KEY) and paste the value. GitHub encrypts and stores it. When an Action runs, GitHub injects it as an environment variable into the server — same mechanism as .env, different delivery.

The design is identical on both sides. On your laptop: .env file. In the cloud: GitHub Secrets. Your code uses os.environ[...] in both cases and doesn't know or care about the difference.

Why This Matters for You

Every tool you've built that talks to an outside service — Anthropic's API, your bank sync, your email agent — has credentials stored somewhere. That somewhere is already environment variables. You just may not have looked closely.

Your email agent lives on a rented server. That server has environment variables set either by Claude Code or by you during deployment — your email password or API token lives there, not in any code file. If it were in a code file, it would have been pushed to graydavis33/my-project on GitHub, which is public.

Your GitHub Actions — the ones that auto-commit your Claude Code sessions and send this email — use GitHub Secrets for any API keys they need. When you view those Action logs, you'll notice secrets are printed as ***. GitHub automatically masks them in output.

Understanding this system means you can now confidently add any new API integration to your tools. You know exactly where the key goes (a .env line on your laptop, a GitHub Secret in the cloud) and why it never touches your code files.

TRY THIS TODAY

Open your project repo and check three things right now:

  1. Find your .gitignore file in the root of your repo. Confirm .env is listed there. If it's not, add it on its own line — right now.
  2. Go to github.com/graydavis33/my-project → Settings → Secrets and variables → Actions. You'll see every secret you or Claude Code have already stored there. Now you know what those actually are and why they're there.
  3. In your project folder on your Mac, press Cmd+Shift+Period in Finder to reveal hidden files. Look for any file starting with a dot named .env. If you find one, that's your local secret shelf — check that it's NOT showing up in git status. If it is, stop and add it to .gitignore before your next push.

Test Yourself

1. In plain English, what is an environment variable?

Answer: A named value that the computer holds in memory — not stored in any code file — that any running program can retrieve by name. Think of it as a labeled bottle on a shelf your recipe (code) can grab without the recipe containing the actual ingredient.

2. Why can't you just put your API key directly in a code file?

Answer: Because code files get pushed to GitHub, which is public. Automated bots scan every public repo hunting for exposed keys, and they will exploit a leaked key within minutes. Putting a secret in your code is like taping your house key to the front door.

3. What does a .env file look like, and where does it live?

Answer: A plain text file literally named .env (dot then "env") in the root of your project folder. Each line is a NAME=value pair. It's hidden in Mac's Finder by default because filenames starting with a dot are treated as hidden system files.

4. What is .gitignore, and what does adding ".env" to it do?

Answer: .gitignore is a file that tells Git which files to completely skip — never track, never commit, never push. Adding .env to it means your secrets file stays on your laptop only, invisible to Git no matter how many times you push.

5. What is a .env.example file and why is it safe to commit to GitHub?

Answer: A copy of .env with all real values replaced by placeholders like your_key_here. It shows anyone reading your repo exactly which environment variables the project needs, without revealing any actual secrets. It's the ingredient list without the recipe.

6. When your code runs in GitHub Actions, it has no access to your local .env file. Where do the secrets come from?

Answer: GitHub Secrets. You add them in your repo's Settings → Secrets and variables → Actions. GitHub stores them encrypted and injects them as environment variables when an Action runs — the cloud equivalent of your local .env file, same mechanism, different delivery.

7. How does Python code actually read an environment variable? Write the two lines needed.

Answer: import os then value = os.environ["VARIABLE_NAME"]. The os module gives your code access to the operating system, and os.environ is a dictionary-like object holding all current environment variables — whether they came from a .env file or GitHub Secrets.

8. You add a Plaid API key to your Payday app. Walk through exactly where that key goes: on your laptop, and in the cloud.

Answer: On your laptop: add PLAID_API_KEY=real_key_here to your local .env file, and confirm .env is in .gitignore. In the cloud: add a secret named PLAID_API_KEY in your repo's GitHub Secrets. Your code uses os.environ["PLAID_API_KEY"] in both environments — it reads from whichever source the current machine provides.

9. You open your repo on GitHub and notice a code file contains the line: smtp_pass = "myActualPassword123". What's the problem, and what do you do first?

Answer: The password has been exposed publicly and must be treated as compromised. Change it immediately on your email provider's site — before fixing anything in the code — because bots may have already grabbed it. Then replace the hardcoded value with os.environ["EMAIL_SMTP_PASS"], add the real value to .env locally and to GitHub Secrets for the cloud, and commit the cleaned code.

10. Why does GitHub print *** instead of actual values when a Secret is used in an Action's log?

Answer: GitHub automatically scans Action log output for strings that match stored Secret values and replaces them with asterisks before the log is saved or displayed. This protects secrets even if a command accidentally echoes them to the console — a second layer of defense beyond just keeping secrets out of code files.
