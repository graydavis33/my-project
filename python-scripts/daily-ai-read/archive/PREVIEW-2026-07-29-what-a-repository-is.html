What a “Repo” Is — The One Concept That Unlocks Everything Else

You have already heard the word “repository” and probably just nodded along. It is the single most important piece of vocabulary in modern software. Once it clicks, GitHub, commits, branches, and half of Claude Code start making sense.

The 2-Minute Version

  • A repository (repo) is a folder that remembers every single change ever made to the files inside it.
  • It does this using software called Git, which is separate from GitHub — Git is the tool, GitHub is a website that stores your Git repos online.
  • Every time you save a snapshot of your work, that is called a commit. Your repo is essentially a stack of those snapshots going back to day one.
  • Repos exist so you can undo anything, try risky changes safely, and share code with collaborators (or with Claude Code) without overwriting each other.
  • Your Payday app and caption scripts are almost certainly living in plain folders right now — today’s issue shows you exactly what you are missing.

Start With the Physical Analogy

Imagine you are editing a client video in Premiere. Good editors do not work in one giant file and pray. They duplicate the project before every big cut, so if something breaks they can roll back. Those duplicates pile up on your drive: ClientVideo_v1, ClientVideo_v2_colorfix, ClientVideo_FINAL, ClientVideo_FINAL_actualfinal.

A repository does that same job — automatically, for every file in your project, with a label and timestamp on each version — without cluttering your drive with duplicate folders. You get the full history without the mess.

The software that powers this is called Git. Git is a version-control system — meaning it is a tool whose only job is to track changes over time. Git was created by Linus Torvalds in 2005 to manage development of the Linux kernel, but today it is used for virtually every serious software project on earth, from solo scripts to billion-dollar apps.

What Is Actually Inside a Repo

When you turn a folder into a Git repository, Git creates a hidden subfolder called .git inside it. That subfolder is the brain. It stores the complete history of every change — who changed what, when, and why. Your actual project files sit right alongside it, unchanged, as they always were.

Each saved snapshot in that history is called a commit. Think of a commit like a labeled bookmark in your timeline. You write a short note when you make it — something like “added invoice calculation” or “fixed the date bug” — and Git records exactly which lines changed. Every commit stores a pointer to its parent commit, so the full project history is a chain of snapshots you can walk backward through at any time.

This means you can always answer the question: “What did this file look like three weeks ago, before I broke it?” With a plain folder, that answer is “gone.” With a repo, it is two commands away.

Git vs. GitHub: They Are Not the Same Thing

This trips up almost everyone. Git is the software that runs on your computer and does the tracking. GitHub is a website — owned by Microsoft — that stores copies of your Git repos online so they are backed up, shareable, and accessible from any machine.

GitHub is a cloud-based hosting service that lets you manage Git repositories. You could use Git entirely offline and never touch GitHub. But in practice, almost everyone pushes their repos to GitHub because it acts as the single source of truth — especially when multiple people (or AI tools) are working on the same code.

When you push, you are uploading your latest commits from your computer to GitHub. When you pull, you are downloading commits someone else added. Those two words will come up constantly, and now you know what they mean.

Why Repos Exist: Three Real Problems They Solve

1. The “I broke everything” problem. You change ten things at once and something stops working. Without a repo, you are guessing which change caused it. With a repo, you can look at the exact lines that changed since your last working commit and pin it down immediately.

2. The “trying something risky” problem. You want to rewrite a big chunk of your script but you are not sure it will work. In a repo, you create a branch — think of it as a parallel copy of your project where experiments live — and try it there. If it works, you merge it back in. If it fails, you delete the branch and nothing in your main code ever changed. (Branches get their own full issue later.)

3. The “Claude Code needs context” problem. Claude Code works directly within your local development environment and can read your project files, edit code, and run commands. When your project lives in a proper repo, Claude Code can see the full file structure and history, make changes, and you can always verify or revert exactly what it did — commit by commit. Without a repo, if Claude Code edits a file and something goes wrong, that original version may simply be gone.

Why This Matters For You

Your Payday app is a real tool you use to manage your income. Your caption scripts run on real client projects. Right now they almost certainly live in plain folders on your machine — no history, no safety net. If Claude Code rewrites a function and it breaks, or your laptop dies, the previous version is gone.

Turning those folders into Git repos takes about 90 seconds per project and gives you a full undo history from that moment forward. It also makes every future Claude Code issue in this newsletter click faster, because terms like “commit,” “push,” and “branch” will already live in your vocabulary.

Try This Today

Open your terminal (the command-line app on your Mac or PC — search “Terminal” on Mac). Navigate into your Payday app folder with the cd command, then run these two lines:

git init
git add .
git commit -m "first snapshot of Payday app"

That is it. Your folder is now a Git repository with one commit — a full snapshot of every file as it exists right now. From this moment forward, every change you make is trackable. (git init creates the repo; git add . stages all files; git commit -m saves the snapshot with a message.)

Test Yourself

1. In one sentence, what is a repository?

Answer: A repository is a folder that uses Git to automatically track and store every change ever made to its files. This matters because it gives you a full undo history without managing duplicate folders manually.

2. What is Git, and who made it?

Answer: Git is version-control software that runs on your computer and tracks changes to files over time. It was created by Linus Torvalds in 2005. It is the engine; GitHub is just a website that stores the repos Git creates.

3. What is a commit?

Answer: A commit is a saved snapshot of your project at a specific moment, labeled with a short message you write. Think of it as a bookmark in your timeline. You can return to any commit at any point.

4. What is the difference between Git and GitHub?

Answer: Git is the software on your computer that does the version tracking. GitHub is a website that stores your repos online for backup and sharing. You can use Git without GitHub, but GitHub requires Git.

5. What does “push” mean in Git?

Answer: Push means uploading your latest commits from your local machine to a remote location like GitHub. It is how your work gets backed up online and made available to others (or to yourself on another device).

6. What is the hidden folder Git creates inside your project, and what does it do?

Answer: It is called .git and it is the entire brain of the repo — it stores the full change history. Your actual project files stay untouched; the .git folder is invisible by default so it does not clutter your workspace.

7. You ask Claude Code to refactor your Payday app’s invoice function. It rewrites it, and the app crashes. Your project is NOT in a repo. What is your situation?

Answer: The original file is likely overwritten and gone. You have no saved snapshot to return to. This is exactly the risk repos prevent — if you had committed before running Claude Code, you could restore the old version in seconds.

8. What is a branch, in simple terms?

Answer: A branch is a parallel copy of your project where you can experiment without touching your main working code. If the experiment works, you merge it in. If it fails, you delete the branch — your main code never changed.

9. What do the three commands git init, git add ., and git commit -m each do?

Answer: git init turns the current folder into a Git repo by creating the .git folder. git add . stages (queues up) all files to be included in the next snapshot. git commit -m "message" actually saves the snapshot with your label. All three are needed for the first commit.

10. Your friend says “just save the file, that’s the same as a commit.” What is wrong with that?

Answer: Saving a file just overwrites the current version — the previous version is gone. A commit keeps the old version intact alongside the new one, labeled and timestamped, forever. Git stores the entire chain of every commit, so you can travel back to any point in the project’s history.
